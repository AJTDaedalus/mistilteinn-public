### [x] R.1a — Genshin parties are four **[unplanned; found while starting R.1]**

The fork inherited a **three-slot** `teams` table because a ZZZ squad is three agents, and its
schema docstring said so in as many words: *"A team is three different characters."* A Genshin
party is **four**.

This is the leaked-shape hazard `CLAUDE.md` names as the fork's main long-term risk — *"no
column that exists because its ZZZ counterpart did"* — and it survived four chunks because
nothing had exercised the table beyond CRUD. Rotations are the first thing that cannot work
around it: a four-character rotation cannot be expressed against three slots at all.

Fixed additively (migration `a71c3e5b9d40`, round-tripped), and the slot names now have **one
definition**, `TEAM_SLOTS`. They had been hand-written in four places — model, schemas,
repository eager-loads, API merge check — which is exactly how three-versus-four went
unnoticed. The duplicate-slot test derives its pairs from that list too, so it now covers all
**six** pairs rather than the three a ZZZ squad has.

### [x] R.1 — The rotation model and its schema — **done; OQ-R1 and OQ-R2 decided**
- **Do:** `rotations` table — name, owner, team (ordered character ids), `steps` JSONB — plus
  the model, repository and migration. Steps validate on the way in: a known action, a
  `repeat` of at least 1, a character that is in the team.
- **OQ-R1 → a team**, and OQ-R2 **→ a step names a character**, both recorded in
  `DECISIONS.md`. The action vocabulary is derived into the committed gcsim snapshot
  (`keys.json`, 13 actions parsed from `action.go`), and the authorable ten come from it by
  subtraction — so a re-pin that adds an action offers it automatically rather than being
  rejected by a list written down here.
- **Accept:** a rotation round-trips; a step naming an unknown action is refused **naming the
  ten that exist**; a step naming a character outside the team is refused; owner scoping is
  covered in `test_owner_scoped_repositories.py` the way `SimRunRepository` is.

### [x] R.2 — The compiler: rotation → gcsim action list — **done**
- **Do:** a pure function, no I/O. `active <first>;`, then `while 1 { … }`, then one
  readiness-gated statement per step, `repeat` as `:n`, **no swap actions** (§3.3).
- **Done.** `app/services/rotation_compiler.py`, pure and session-free. `active` is the
  **first step's** character rather than the team's first slot, so a rotation does not open
  with an implicit swap the user did not write. Every step is gated, *including* `attack`:
  gating selectively would need a hand-kept table of "which actions can stall", and a wrong
  entry there brings the deadlock back silently.
- A stale step is refused with **every** offending step named, not the first — the same
  reasoning the GOOD importer uses when it reports each rejected artifact.
- **Injections:** dropping the gates fails 2, dropping the loop fails 1, silently dropping
  stale steps fails 2. Both of D.2's silent gcsim behaviours are now regression-tested at the
  compiler; R.3 tests them against gcsim itself.

### [x] R.3 — The compiler is checked by gcsim, not by us **[gate]** — **done**
- **Do:** extend the `gcsim:verify-config` harness so compiled rotations are fed to real
  gcsim at the pin, and add a **cycle-count** assertion: read `statistics.character_actions`
  back and require the rotation to have run more than once over the configured duration.
- **Done, and the numbers are the argument.** The compiled rotation and a deliberately
  **ungated control** are both emitted, both **accepted by gcsim**, and then *run*:

  | config | actions over 90s |
  |---|---|
  | `rotation_gated` | `attack 146, burst 2, skill 9` |
  | `rotation_ungated` | `attack 3, burst 1, skill 1` |

  The control is generated by stripping the compiler's own output rather than by a second
  emitter — two generators would drift, and the one that drifted would leave the gate
  comparing the real config against a stale idea of what "wrong" looks like.
- **The gate fails in both directions**, verified: a gated config that runs once fails, and a
  control that *stops* running once fails too, because that would mean the check is measuring
  nothing. Exit code confirmed `1` rather than a printed error and a green exit.
- **Why it is its own task:** acceptance by gcsim is not evidence of correctness. Both ER-sweep
  failures produced configs gcsim accepted happily.

### [x] R.4 — The API — **done** (`75bfb22`)
- **Do:** CRUD under `/api/v1/rotations`, owner-scoped, plus `POST /rotations/{id}/compile`
  returning the emitted config for inspection.
- **Accept:** every new route added to the 401 sweep **in the same commit** —
  `test_the_sweep_covers_every_owned_route` fails otherwise, which is the point; `openapi.json`
  regenerated; the contract test green.
- **Done:** six routes; the write path refuses a step naming someone off the team (422 on both
  POST and PATCH, `scripts.inject` confirms three tests hold it); `/compile` refuses a stale
  rotation and leaves the authored steps intact. 14 integration tests. `openapi.json` at 29
  paths. Verified locally: 1034 passed / 0 skipped, `ci_local` 19/19.

### [x] R.5 — The editor — **done**
- **Do:** a page to build a rotation: pick a team, add steps, reorder, set `repeat`, save.
  Uses `catalogue-list.ts`'s error discipline and the Mitya tokens.
- **Accept:** reachable from the shell nav — `app.routes.spec.ts` fails otherwise; a failed
  load is surfaced rather than rendered as "no results"; the compiled config is viewable, so a
  user can see what their rotation became.
- **Done:** `pages/rotations/`, plus `GET /rotations/options` — the editor needs the action
  vocabulary and each team's roster keyed by `nanoka_id`, and deriving the latter on the
  client meant five round trips and a UUID→`nanoka_id` mapping it has no business doing.
  Picker and validator read one source, tested as one. Nav link added; `app.routes.spec.ts`
  passes. 12 component tests; two mutations CAUGHT, one SURVIVED and the unfailable test it
  exposed was removed rather than kept.

### [x] R.6 — Wire it to the run corpus — **done**
- **Do:** a saved rotation feeds `sim_context.context_key` and the D.1 corpus, so a rotation
  and a team together identify a cached run.
- **Accept:** two rotations differing by one step produce different context keys; the same
  rotation reordered produces a different key — `context_key` already treats rotation order as
  significant, and this proves the compiler agrees.
- **Done:** `POST /rotations/{id}/context-key`. `rotation_signature` shares `_resolve` with
  the compiler, and `gcsim_config.target_fields` is now shared with the target line, so
  neither the rotation nor the target can be described two ways. Both acceptance criteria are
  tests, and both survive mutation: sorting the signature and dropping `repeat` are CAUGHT.
